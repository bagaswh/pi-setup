# LangGraph (Python) Checkpointing: How It Works

Research brief on how `langchain-ai/langgraph` (Python, `main` branch as of 2026-10) implements checkpointing. LangGraph's durability is built on a single abstraction — `BaseCheckpointSaver` — driven by the Pregel execution loop. Every superstep of a graph run produces a full state **checkpoint** scoped to a **thread** (`thread_id`) and a **checkpoint namespace** (`checkpoint_ns`); node outputs are persisted as **pending writes** (`put_writes`) against the in-progress checkpoint, and the finished superstep is committed with `put`. State is serialized with an ormsgpack-based `JsonPlusSerializer` (opt-in pickle fallback; `LANGGRAPH_STRICT_MSGPACK` hardening), and human-in-the-loop interrupts, crash resume, and time-travel are all implemented as thin layers over these two write paths. All claims below cite the actual source files or official docs; version-drift caveats are flagged inline.

**Path note:** in current `main`, the checkpointer interface is at `libs/checkpoint/langgraph/checkpoint/base/__init__.py` (a package, not `base.py`) and the in-memory saver at `libs/checkpoint/langgraph/checkpoint/memory/__init__.py`. The Pregel loop that drives the checkpointer is `libs/langgraph/langgraph/pregel/_loop.py` (with `main.py` orchestrating and `pregel/_runner.py` committing per-task writes). The `ordered_map` / `ordered_list` / `ordered_sets` checkpoint fields and the `next_id`/`setup` base-methods described in older blog posts no longer exist in current `main` (verified by reading the files; see §3).

## 1. Architecture

### 1.1 What a checkpoint is

A checkpoint is a `TypedDict` snapshot of every channel's state plus the version bookkeeping the Pregel loop needs to decide what runs next (`libs/checkpoint/langgraph/checkpoint/base/__init__.py::Checkpoint`):

```python
class Checkpoint(TypedDict):
    v: int                 # format version (docstring says "Currently 1";
                           # pregel/_checkpoint.py::LATEST_VERSION = 4 as of main)
    id: str                # UUIDv6 — unique AND monotonically increasing,
                           # so checkpoints sort first→last
    ts: str                # ISO 8601 creation timestamp
    channel_values: dict[str, Any]        # channel name -> snapshot value
    channel_versions: ChannelVersions     # channel -> monotonic version
    versions_seen: dict[str, ChannelVersions]  # node -> (channel -> version seen)
    updated_channels: list[str] | None    # channels updated in this checkpoint
```

(source: base/__init__.py::`Checkpoint`; base/__init__.py::`ChannelVersions = dict[str, str | int | float]`)

Field semantics, per the docstrings:

- **`id`** — "both unique and monotonically increasing, so can be used for sorting checkpoints from first to last" (base/__init__.py::`Checkpoint.id`). It is a **UUIDv6** generated by `uuid6(clock_seq=step)` in `pregel/_checkpoint.py::create_checkpoint`; the bundled implementation (`base/id.py::uuid6`, adapted from the `uuid6` package) guarantees monotonicity by bumping the timestamp if it would go backwards. This is why every SQL schema can do `ORDER BY checkpoint_id DESC LIMIT 1` to fetch the latest checkpoint and `checkpoint_id < %s` for "before" queries (checkpoint-postgres/base.py::`_search_where`; SqliteSaver docstrings).
- **`channel_values`** — the values of state channels at snapshot time. The Pregel runtime materializes graph state as *channels* (LastValue, Topic, BinaryOperatorAggregate, etc.), so a checkpoint is the channel-level state, not the user-visible state dict.
- **`channel_versions` / `versions_seen`** — the core of the trigger algorithm: "Map from node ID to map from channel name to version seen. This keeps track of the versions of the channels that each node has seen. Used to determine which nodes to execute next" (base/__init__.py::`Checkpoint.versions_seen`). A node is scheduled when a channel it subscribes to has a version higher than the version the node last saw (`_algo.py::prepare_next_tasks`).
- **`updated_channels`** — a newer field listing which channels were updated in this checkpoint (used as a trigger hint; `pregel/_loop.py` threads it into `prepare_next_tasks`).
- **`v`** — format version. Note a docstring inconsistency: `base/__init__.py` says "Currently `1`", but `pregel/_checkpoint.py::LATEST_VERSION = 4` and the JS implementation writes `v: 4` — treat the base docstring as stale (contradiction recorded in §7).
- **`pending_sends`** — appears only in deprecated legacy helpers at the bottom of base/__init__.py (`empty_checkpoint()` marked "deprecated utilities used by past versions of LangGraph"); current `create_checkpoint` does not emit it. The `ordered_map`/`ordered_list`/`ordered_sets` fields mentioned in some third-party writeups do not exist in current `main` at all (not found in base/__init__.py nor pregel/_checkpoint.py).

Alongside the checkpoint, each save carries **`CheckpointMetadata`** (a `total=False` TypedDict): `source` (`"input" | "loop" | "update" | "fork"`), `step` (`-1` for the first input checkpoint, `0` for the first loop checkpoint, then n), `parents` (namespace → parent checkpoint id map, i.e. the `checkpoint_map`), `run_id`, and — new, beta — `counters_since_delta_snapshot` backing `DeltaChannel` (base/__init__.py::`CheckpointMetadata`).

### 1.2 What a thread is

"A thread is a unique ID or thread identifier assigned to each checkpoint saved by a checkpointer. It contains the accumulated state of a sequence of runs" (docs: checkpointers.md, "Threads"). The checkpointer "uses `thread_id` as the primary key for storing and retrieving checkpoints" (same page; base/__init__.py::`BaseCheckpointSaver` class docstring says the same). Concretely, in every backend the primary key starts with `(thread_id, checkpoint_ns, checkpoint_id)`:

- SQLite: `PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)` (checkpoint-sqlite/__init__.py::`setup`)
- Postgres: same columns (`checkpoint-postgres/base.py::MIGRATIONS`)
- InMemory: `storage: defaultdict[thread_id, dict[ns, dict[cid, ...]]]` (memory/__init__.py)

Usage guidance from the base docstring: a unique `thread_id` per run for single-shot workflows; a reused `thread_id` for conversational memory.

### 1.3 How the identifiers relate

- **`thread_id`** — the top-level key. All checkpoints (parent and subgraph), writes, and blobs of one conversation/run share it. It lives in `config["configurable"]["thread_id"]` (`_internal/_constants.py::CONFIG_KEY_THREAD_ID`).
- **`checkpoint_id`** — identifies one checkpoint *within* a thread. Absent from config means "latest" (savers do `ORDER BY checkpoint_id DESC LIMIT 1`); present means "this exact checkpoint" (time travel).
- **`checkpoint_ns`** — the checkpoint *namespace*: `""` for the parent (root) graph, `"node_name:task_id"` for a subgraph invoked as that node, and `"outer:uuid|inner:uuid"` for nested subgraphs (docs: checkpointers.md "Checkpoint namespace"; `_constants.py`: `NS_SEP = "|"`, `NS_END = ":"`). Subgraph state is therefore stored **in the parent thread** under a namespaced key, not in a separate thread. `__enter__` of the loop splits the ns on `|` (`_loop.py::PregelLoop.__init__`, `self.checkpoint_ns = tuple(...split(NS_SEP))`).
- **`checkpoint_map`** — a config key mapping each relevant namespace to its checkpoint id, so a parent replaying from an old checkpoint can find the matching subgraph checkpoints (`_constants.py::CONFIG_KEY_CHECKPOINT_MAP`; used in `_loop.py.__enter__` and `_first`; persisted as metadata `parents`).
- **`task_id`** — not a checkpoint coordinate, but the key for pending writes: each node execution within a superstep persists its writes under its task id, keyed `(thread_id, checkpoint_ns, checkpoint_id, task_id, idx)`.

A `CheckpointTuple` (NamedTuple) is what savers return on read: `config`, `checkpoint`, `metadata`, `parent_config`, `pending_writes` (base/__init__.py::`CheckpointTuple`).

## 2. When checkpoints are written

The engine touches the checkpointer through exactly two write methods — `put_writes` (per-task, during a superstep) and `put` (per-superstep, at boundaries) — plus `get_tuple` reads at loop entry.

### 2.1 Per-task writes: `put_writes`

`PregelRunner.commit()` is the callback invoked when each node task finishes (`pregel/_runner.py::PregelRunner.commit`). On success it calls `self.put_writes()(task.id, task.writes)` — persisting that node's channel writes immediately, before the superstep completes. Special cases write to reserved channels (`_internal/_constants.py`): a `GraphInterrupt` saves `("__interrupt__", interrupts)` (plus any cached `__resume__` writes); a node error saves `("__error__", exception)` and, when the node has an error handler, `("__error_source_node__", node_name)`; a task that wrote nothing saves `("__no__writes__", None)` so its completion is still recorded.

`PregelLoop.put_writes` then (a) deduplicates writes to reserved channels, (b) appends them to the in-memory `checkpoint_pending_writes` list, and (c) persists them via the checkpointer in a **background thread/executor** (`self.submit(self.checkpointer_put_writes, config, writes_to_save, task_id, task_path)`) — but only `if self.durability != "exit"` (`_loop.py::PregelLoop.put_writes`). The config is patched so the writes attach to the *current* checkpoint id. This is the mechanism the docs call "pending writes": "As each node within a super-step finishes, its outputs are written to the checkpointer's `checkpoint_writes` table as task entries linked to the in-progress checkpoint. … if another node in the same super-step fails, the successful nodes' writes are already durable and don't need to be re-run on resume" (docs: checkpointers.md).

Writes to special channels are indexed with negative idx values so they never collide with regular writes: `WRITES_IDX_MAP = {ERROR: -1, SCHEDULED: -2, INTERRUPT: -3, RESUME: -4}` (base/__init__.py::`WRITES_IDX_MAP`; used by all savers' `put_writes`).

### 2.2 Per-superstep commit: `put`

`PregelLoop.tick()` plans the superstep's tasks, and `after_tick()` finishes it: it applies all task writes to the in-memory channels (`_algo.py::apply_writes`), clears `checkpoint_pending_writes`, then calls `self._put_checkpoint({"source": "loop"})` (`_loop.py::PregelLoop.after_tick`). So **one checkpoint per superstep**, by construction — the docs state it directly: "LangGraph creates a checkpoint at each super-step boundary … For a sequential graph like `START -> A -> B -> END`, there are separate super-steps for the input, node A, and node B — producing a checkpoint after each one" (checkpointers.md). Their worked example yields exactly 4 checkpoints (empty/input, after A, after B) for that graph.

There are four call sites of `_put_checkpoint`, each with a different `source` (`_loop.py`):

1. `PregelLoop._first` → `{"source": "input"}` — after mapping the invocation input to channel writes (first checkpoint of a run; `step` stays such that input checkpoint metadata shows `step: -1`).
2. `PregelLoop.after_tick` → `{"source": "loop"}` — after each superstep's writes are applied.
3. `PregelLoop._first` → `{"source": "fork"}` — when time-traveling to a checkpoint the thread has moved past (or a non-update/fork checkpoint), a fork checkpoint is saved immediately so the replayed execution starts a new branch (also clears stale `__interrupt__` writes; comment: "Without this, if the execution hits an interrupt before after_tick() runs, no new checkpoint is created"). `update_state` (graph-level API) creates `{"source": "update"}` checkpoints via the same machinery (`pregel/main.py`).
4. `PregelLoop._suppress_interrupt` (the context-manager exit hook) — **exit commit** in `durability == "exit"` mode: calls `_put_checkpoint(self.checkpoint_metadata)` plus `_put_exit_delta_writes()` and `_put_pending_writes()` when the run exits (normally, on error, or on interrupt). This call is detected by object identity (`metadata is self.checkpoint_metadata`) and reuses the already-generated checkpoint id; if `checkpoint["id"] == checkpoint_id_saved` it returns early — "checkpoint already saved" — the one place a redundant save is skipped (`_loop.py::_put_checkpoint` opening comment).

Inside `_put_checkpoint`, `create_checkpoint()` (pregel/_checkpoint.py) snapshots the live channels into a new `Checkpoint` (new `uuid6(clock_seq=step)` id), the previous config becomes `parent_config`, and the save is submitted to the background executor **chained on the previous save's future**:

```python
# save it, without blocking
# if there's a previous checkpoint save in progress, wait for it
# ensuring checkpointers receive checkpoints in order
self._put_checkpoint_fut = self.submit(
    self._checkpointer_put_after_previous,
    getattr(self, "_put_checkpoint_fut", None),
    self.checkpoint_config, copy_checkpoint(self.checkpoint),
    self.checkpoint_metadata, new_versions,
)
```
(`_loop.py::_put_checkpoint`; `SyncPregelLoop._checkpointer_put_after_previous` does `prev.result()` then `checkpointer.put(...)` — same for the async variant with `asyncio` futures.)

### 2.3 What triggers a checkpoint, and what doesn't

- A superstep that plans **zero tasks** ends the run (`tick()` sets status "done" and returns False) — no new checkpoint for the final empty tick.
- A superstep whose nodes write nothing still produces a `source="loop"` checkpoint: `do_checkpoint` in `_put_checkpoint` is `self._checkpointer_put_after_previous is not None and (exiting or self.durability != "exit")` — it does **not** inspect whether any channel changed. There is **no identical-state/digest optimization** in the current loop: every executed superstep writes a full new checkpoint row. (Researcher inference from absence: I found no digest/hash-based skip anywhere in `_loop.py`/`_checkpoint.py`; the only "already saved" skip is the exit-mode id check.) The storage-side mitigation is the beta `DeltaChannel` (see §2.5) and Postgres's blob dedup (`ON CONFLICT … DO NOTHING` keyed by `(channel, version)` — identical channel values across checkpoints are stored once; checkpoint-postgres/base.py::`UPSERT_CHECKPOINT_BLOBS_SQL`).
- Interrupts (`interrupt_before`/`interrupt_after` node lists, or dynamic `interrupt()`) raise `GraphInterrupt` from `tick`/`after_tick`; the exception unwinds to `_suppress_interrupt`, which persists the current checkpoint + pending writes (always in exit mode; in async/sync mode the last `put` already happened or is in flight) and suppresses the exception. The interrupt payload itself was already persisted as a `__interrupt__` pending write by the runner's `commit`.
- `Command(resume=...)` inputs map to `("__resume__", value)` writes per task id via `put_writes` in `_first` (`_loop.py::_first`); resuming also requires a checkpointer — `"Cannot use Command(resume=...) without checkpointer"` raises otherwise.

### 2.4 Durability modes: sync / async / exit

Durability is a per-invocation argument on `invoke`/`stream`/etc., defaulting to `"async"` (`pregel/main.py::_defaults`: `durability = config.get(CONF, {}).get(CONFIG_KEY_DURABILITY, "async")`; the docstring in main.py: `"sync"`: "persisted synchronously before the next step starts", `"async"`: "persisted asynchronously while the next step executes", `"exit"`: "persisted only when the graph exits"). It replaces the old `checkpoint_during` flag (`checkpoint_during=False` ≙ `durability="exit"`; main.py emits a deprecation warning mapping it). Docs summary (checkpointers.md "Durability modes"): `"exit"` = best performance, no mid-run recovery; `"async"` = good performance, small crash window; `"sync"` = every checkpoint durable before the next step starts.

Mechanically (`_loop.py` + `main.py`):

- **`"exit"`**: `put_writes` calls are skipped during the run (`if self.durability != "exit" and self.checkpointer_put_writes is not None`); `_put_checkpoint` computes `do_checkpoint = … and (exiting or self.durability != "exit")` so intermediate supersteps only bump delta-channel counters in memory, and the single final commit happens in `_suppress_interrupt` at context exit (which also flushes accumulated `_exit_delta_writes` and remaining pending writes). A top-level graph, a nested graph with error/interrupt, or a subgraph compiled with `checkpointer=True` commits on exit.
- **`"async"` (default)**: `put`/`put_writes` are submitted to a `BackgroundExecutor`; the next superstep proceeds while persistence runs. Checkpoints are still ordered by the future-chaining in `_checkpointer_put_after_previous`.
- **`"sync"`**: identical submission, but after each superstep the orchestrator blocks on the checkpoint future — `loop.after_tick()` is followed by `if durability_ == "sync": loop._put_checkpoint_fut.result()` (async: `await loop._put_checkpoint_fut`) in `pregel/main.py`'s stream loop.

So persistence is asynchronous/batched by default at the engine level, with explicit futures when sync is requested. There is no cross-superstep *write batching* of `put` calls (one `put` per superstep, ordered), but `put_writes` from parallel tasks within a superstep do run concurrently in the background executor.

### 2.5 Storage growth control: DeltaChannel (beta)

By default "checkpoints write the full value of every state channel at each super-step", which "can produce significant storage growth over time" for append-heavy channels like `messages` (docs: checkpointers.md "Optimize checkpoint storage"). `DeltaChannel` (beta, `langgraph>=1.2`) stores only incremental deltas: the checkpoint keeps a `_DeltaSnapshot` sentinel blob, written every `snapshot_frequency` updates or after `DELTA_MAX_SUPERSTEPS_SINCE_SNAPSHOT` (default 5000, env-tunable) supersteps; on load, `channels_from_checkpoint` reconstructs the value by walking ancestors via `BaseCheckpointSaver.get_delta_channel_history` (seed `_DeltaSnapshot` + accumulated `checkpoint_writes`) and replaying them through the channel's reducer (pregel/_checkpoint.py::`channels_from_checkpoint`, `delta_channels_to_snapshot`; base/__init__.py::`CheckpointMetadata.counters_since_delta_snapshot` docstring). This is the only built-in mechanism that avoids O(state) bytes per superstep.

## 3. The interface

`BaseCheckpointSaver(Generic[V])` (base/__init__.py) is a plain class — **none of the methods are Python-abstract**; unimplemented ones raise `NotImplementedError` *at call time* (a design gotcha: a custom saver that misses a method fails only when the engine calls it). The full surface:

**Write path**

| Method | Required? | What it must do (per docstring) |
|---|---|---|
| `put(config, checkpoint, metadata, new_versions) -> RunnableConfig` | required (raises) | "Store a checkpoint with its configuration and metadata." `new_versions` = "New channel versions as of this write." Returns updated config pointing at the saved checkpoint id. |
| `put_writes(config, writes, task_id, task_path="")` | required (raises) | "Store intermediate writes linked to a checkpoint." `writes` = `(channel, value)` pairs; `task_id` = "Identifier for the task creating the writes"; `task_path` (newer, optional-capability arg) = task's path. Implementations should use `WRITES_IDX_MAP` for special channels. |
| `aput`, `aput_writes` | required for async | async twins; the engine picks sync vs async based on how the graph is invoked (docs: checkpointers.md "Checkpointer interface"). |

**Read path**

| Method | Required? | Notes |
|---|---|---|
| `get(config) -> Checkpoint \| None` | **has default** | implemented as `if value := self.get_tuple(config): return value.checkpoint`. |
| `get_tuple(config) -> CheckpointTuple \| None` | required (raises) | must support both "latest for thread(+ns)" and "exact checkpoint_id" lookups (docs stress the exact-id path is load-bearing for time travel and DeltaChannel reconstruction). |
| `list(config, *, filter=None, before=None, limit=None)` | required (raises) | "List checkpoints that match the given criteria"; `filter` = metadata equality filter; `before` = only checkpoints older than that config's id; newest first. |
| `aget`, `aget_tuple`, `alist` | required for async | async twins. |

**Thread lifecycle (extended capabilities)**

| Method | Required? | Notes |
|---|---|---|
| `delete_thread(thread_id)` | required (raises) | "Delete all checkpoints and writes associated with a specific thread ID." |
| `delete_for_runs(run_ids)` | raises (optional) | deletes checkpoints/writes for given run ids — enables Agent Server "rollback multitask strategy" (docs: checkpointers.md "Extended capabilities" table). |
| `copy_thread(source, target)` | raises (optional) | "Copy all checkpoints and writes from one thread to another" — efficient forking; must copy the **complete parent chain** or DeltaChannel state breaks (docstring warning). |
| `prune(thread_ids, *, strategy="keep_latest")` | raises (optional) | history pruning; docstring carries a long DeltaChannel warning (keep_latest must not sever the ancestor write chain). |

**Delta channels (beta)**

| Method | Required? | Notes |
|---|---|---|
| `get_delta_channel_history(*, config, channels) -> Mapping[str, DeltaChannelHistory]` | **has default** | walks `get_tuple` + `parent_config` once for all channels, collecting per-channel `writes` and terminating each channel at the nearest ancestor with a stored value (`seed`); async twin `aget_delta_channel_history`. InMemory, SQLite and Postgres override with two-query fast paths. |

**Other members**

- `serde: SerializerProtocol = JsonPlusSerializer()` — class attribute; `__init__(*, serde=None)` lets you inject a custom serializer (all savers take `serde=`).
- `config_specs` property — returns `[]` by default (declares config options; used by the platform).
- `get_next_version(current, channel=None) -> V` — **has default**: integer versions incrementing by 1; `str` versions raise `NotImplementedError` ("override … as long as they are monotonically increasing"). InMemory/SQLite/Postgres all override it with a `"%032d.%016d"`-style string (`f"{next_v:032}.{next_h:016}"`, memory/__init__.py) so versions sort correctly across processes.
- `with_allowlist(extra_allowlist)` — returns a shallow clone with a merged msgpack deserialization allowlist (strict-mode support).
- Module-level helpers all savers use: `get_checkpoint_id(config)`, `get_checkpoint_metadata(config, metadata)` (merges config metadata, strips NUL chars from strings, excludes `EXCLUDED_METADATA_KEYS`), `get_serializable_checkpoint_metadata` (drops the non-serializable `writes` key — used by Postgres), `WRITES_IDX_MAP`, `CheckpointTuple`, `PendingWrite = tuple[str, str, Any]`.

**Not in the base interface (contrary to older articles):** `setup()`, `next_id()`, `get_next_version` being abstract. `setup()` exists only on the DB savers (SqliteSaver.setup creates tables lazily via its `cursor()` context manager; PostgresSaver.setup "MUST be called directly by the user the first time" and runs the `MIGRATIONS` list, checkpoint-postgres/__init__.py::`setup`). Checkpoint ids are generated by the engine (`create_checkpoint` → `uuid6`), not by the saver — there is no `next_id` anywhere in current base.

## 4. Serialization

### 4.1 `JsonPlusSerializer`: ormsgpack with typed envelopes

Despite the name, `JsonPlusSerializer` (serde/jsonplus.py) is **ormsgpack-based**. `dumps_typed(obj) -> (type_tag, bytes)` returns one of: `("null", b"")` for None, `("bytes", obj)`, `("bytearray", obj)`, `("msgpack", _msgpack_enc(obj))` for everything else, or `("pickle", pickle.dumps(obj))` **only if** `pickle_fallback=True` and msgpack encoding raised (`serde/jsonplus.py::dumps_typed` — the default constructor takes `pickle_fallback: bool = False`, so pickle is opt-in). `loads_typed` dispatches on the tag: legacy `("json", …)` payloads (written before the msgpack migration) go through a `json.loads` reviver with an `allowed_json_modules` allowlist; `("msgpack", …)` goes through `ormsgpack.unpackb(ext_hook=…)`.

The msgpack encoder (`_msgpack_default`) handles rich types via **ext codes** 0–7:

```python
EXT_CONSTRUCTOR_SINGLE_ARG = 0   # (module, name, arg)
EXT_CONSTRUCTOR_POS_ARGS   = 1   # (module, name, (args...))
EXT_CONSTRUCTOR_KW_ARGS    = 2   # (module, name, {kwargs})
EXT_METHOD_SINGLE_ARG      = 3   # (module, name, arg, method)
EXT_PYDANTIC_V1            = 4
EXT_PYDANTIC_V2            = 5
EXT_NUMPY_ARRAY            = 6
EXT_DELTA_SNAPSHOT         = 7
```

Types that round-trip natively (each encoded as `(module, class, payload)` constructor records): **pydantic v2 models** (`model_dump` + `model_validate_json`), **pydantic v1** (`.dict()`), objects with `get_secret_value` (secrets), **namedtuples** (`_asdict` → kwargs), `pathlib.Path` (parts), `re.Pattern` (`re.compile`), `uuid.UUID` (hex), `decimal.Decimal` (str), `set`/`frozenset`/`collections.deque` (tuple), `IPv4/6 Address/Interface/Network` (str), `datetime` (isoformat + `fromisoformat`), `timedelta` (d/s/µs), `date`, `time` (kwargs incl. tzinfo/fold), `timezone`, `zoneinfo.ZoneInfo` (key), `Enum` (value), `langgraph.types.Send` (node/arg/timeout), **dataclasses** (field dict), `langgraph.store.base.Item`, **numpy arrays** (dtype/shape/order/memoryview), and `BaseException` (stored as `repr()` — a lossy one-way encoding). Anything else raises `TypeError("Object of type … is not serializable")` unless pickle fallback is on.

### 4.2 Security: allowlists and `LANGGRAPH_STRICT_MSGPACK`

The class docstring carries an explicit warning: "This serializer is intended for use within the `BaseCheckpointSaver` class … It should not be used on untrusted python objects. If an attacker can write directly to your checkpoint database, they may be able to trigger code execution when data is deserialized" (serde/jsonplus.py). Hardening layers:

- **`LANGGRAPH_STRICT_MSGPACK=true`** (env var, read at import in serde/_msgpack.py::`STRICT_MSGPACK_ENABLED`) restricts deserialization to the built-in `SAFE_MSGPACK_TYPES` frozenset: datetime/date/time/timedelta/timezone, `uuid.UUID`, `decimal.Decimal`, set/frozenset/deque, ipaddress types, pathlib paths (incl. py3.13 `pathlib._local`), ZoneInfo, `re.compile`, the langchain-core message types (HumanMessage, AIMessage, SystemMessage, ToolMessage, …), `Document`, and langgraph's `Send`, `Interrupt`, `Command`, `Overwrite`, `StateSnapshot`, `PregelTask`, `TimeoutPolicy`, store `Item`/`GetOp` (serde/_msgpack.py::`SAFE_MSGPACK_TYPES`).
- **Default (permissive) mode** warns but allows unregistered types: "Deserializing unregistered type %s.%s from checkpoint. This will be blocked in a future version. Set LANGGRAPH_STRICT_MSGPACK=true to block now, or add to allowed_msgpack_modules" (`_create_msgpack_ext_hook`), with dedup + a 1000-type cap on warning volume.
- **`allowed_msgpack_modules`** constructor arg / `with_msgpack_allowlist` / `BaseCheckpointSaver.with_allowlist` for explicit allowlisting. This is the mitigation story around the msgpack deserialization advisory the parent context referenced (GHSA-g48c-2wqr-h844; I verified the hardening code but not the advisory text itself — flagged in §7). A second advisory is referenced in-code: method-field dispatch on lc:2 JSON envelopes was removed for GHSA-fjqc-hq36-qh5p (jsonplus.py::`_revive_lc2` comment).
- **Method calls** are gated separately: only `("datetime", "datetime", "fromisoformat")` is in `SAFE_MSGPACK_METHODS` (serde/_msgpack.py).
- Legacy `("json", …)` checkpoints are revived via `langchain_core.load.Reviver` behind `allowed_json_modules`, with the same safe-type bypass (`_is_safe_json_type`).

### 4.3 How serde plugs into the savers

Every `BaseCheckpointSaver.__init__(*, serde=None)` stores `maybe_add_typed_methods(serde or self.serde)`; savers then call `self.serde.dumps_typed(...)`/`loads_typed(...)` for checkpoints, blobs, and writes. Backend differences:

- **Postgres** splits each checkpoint: primitive channel values (`None`/`str`/`int`/`float`/`bool`) stay inline in the `checkpoints` row's `checkpoint` JSONB; everything else is moved to `checkpoint_blobs` keyed `(thread_id, checkpoint_ns, channel, version)` (checkpoint-postgres/__init__.py::`put`) — blob rows are `ON CONFLICT DO NOTHING`, so an unchanged value shared by many checkpoints is stored once. `_DeltaSnapshot` values leave a literal `true` marker inline. Metadata is stored as JSONB via `get_serializable_checkpoint_metadata` (drops the `writes` key). The read path (`SELECT_SQL`) reassembles channel values by joining `channel_versions` against blobs and aggregates pending writes in one SQL statement.
- **InMemory** mirrors this with a `blobs` dict keyed `(thread_id, ns, channel, version)`; the checkpoint dict is stored with `channel_values` popped out (memory/__init__.py::`put`), and `get_tuple` rehydrates via `_load_blobs`.
- **SQLite** stores `channel_values` inline in the serialized checkpoint BLOB and metadata as a JSON string (`json.dumps(get_checkpoint_metadata(...))`) — no blobs table (checkpoint-sqlite/__init__.py::`put`).
- `EncryptedSerializer` (wrapping any inner serde with a `CipherProtocol`, e.g. `from_pycryptodome_aes()` reading `LANGGRAPH_AES_KEY`) can be passed as `serde=` to any saver; on LangSmith deployments encryption auto-enables when the env var is present (docs: checkpointers.md "Encryption").

**Note on `lc_len`:** the parent-context brief mentioned "lc_len serialization in metadata" — no `lc_len` handling exists in current main's jsonplus.py or the savers I read (metadata is plain JSON/JSONB/typed-serde as above). That detail appears to be from an older LangGraph version; treat it as stale.

### 4b. The JS implementation

The JS `BaseCheckpointSaver` (langgraphjs `libs/checkpoint/src/base.ts`) is structurally similar but differs in several ways:

- **Everything is async.** There are no sync methods at all — `getTuple`, `list`, `put`, `putWrites`, `deleteThread` are all `abstract` **async** methods (and genuinely `abstract`, enforced at compile time, unlike Python's raise-at-runtime). `putWrites` **does exist** (camelCase), so the "JS has no put_writes" claim is false for current code; what JS lacks is the extended capability surface: no `delete_for_runs`, `copy_thread`, `prune`, or `setup`.
- **No msgpack.** The JS `JsonPlusSerializer` (serde/jsonplus.ts) is pure JSON: `dumpsTyped` returns `["json", bytes]` (or `["bytes", ...]`), using a safe-stringify replacer that emits `lc: 2` constructor records for `Set`, `Map`, `RegExp`, `Error`, `Uint8Array`, `undefined`, and `DeltaSnapshot`; the reviver reconstructs only that closed set of types and keeps everything else inert — no arbitrary import-and-construct like Python's msgpack ext hook, hence no strict-mode env var.
- **Checkpoint shape:** same five core fields (`v` (4), `id` (uuid6), `ts`, `channel_values`, `channel_versions`, `versions_seen`) but no `updated_channels`; JS also accepts a legacy `thread_ts` alias for `checkpoint_id` (`getCheckpointId`). It adds a `toJSON()` guard so a checkpointer in config never stringifies a DB pool.
- Consequence (researcher inference, not stated in sources): Python and JS checkpoints are **not** cross-compatible at the storage level — different serializations and (for Postgres) different schema generations.

## 5. HITL & durability features

### 5.1 How interrupts are persisted

When a node calls `interrupt(...)`, it raises `GraphInterrupt` carrying the payload(s). `PregelRunner.commit` catches it and persists, via `put_writes`, the writes `[(INTERRUPT, interrupts)]` — i.e. the interrupt payload is stored as a **pending write on the special `__interrupt__` channel** (idx −3 via `WRITES_IDX_MAP`), linked to the current in-progress checkpoint and the interrupting task's id (pregel/_runner.py::`commit`: "save interrupt to checkpointer"). The docs describe the runtime contract: "Graph execution gets suspended … State is saved using the checkpointer … Value is returned to the caller … under `__interrupt__` with the default `invoke()` API … Graph waits indefinitely until you resume" (docs: interrupts.md). `GraphInterrupt` is a `GraphBubbleUp` subclass that `_panic_or_proceed` aggregates across parallel tasks and re-raises once, so all concurrent interrupts are captured in one `__interrupt__` write; the loop's exit hook `_suppress_interrupt` then persists the checkpoint + pending writes (in exit mode explicitly; otherwise they're already durable) and suppresses the exception, setting `status = "interrupt_before"/"interrupt_after"`.

### 5.2 Resume after interrupt or failure

- **Resuming with a value:** `graph.invoke(Command(resume=X), config)` — `_first` detects the Command input, maps it to per-task `("__resume__", X)` writes (idx −4) via `put_writes`, and marks all current channel versions as seen by the pseudo-node `"__interrupt__"` (`self.checkpoint["versions_seen"].setdefault(INTERRUPT, {})`) so nothing else re-triggers. With multiple pending interrupts you must pass a dict keyed by interrupt id (`Command(resume={id: value})`; ids are xxh3-128 hexdigests, checked by `is_xxh3_128_hexdigest` — otherwise: "When there are multiple pending interrupts, you must specify the interrupt id when resuming", _loop.py::_first). On the next tick, the interrupted task re-executes and the cached `__resume__` write is returned as `interrupt()`'s return value (`read_task_statuses` in _task_status.py reconstructs pending interrupts/returns from pending writes).
- **Same thread required:** "You must use the same thread ID when resuming that was used when the interrupt occurred" (docs: interrupts.md).
- **Crash resume / pending writes of succeeded siblings:** because each successful task's writes were persisted by `put_writes` at commit time, a run that dies mid-superstep (one sibling failed, process crashed) leaves the checkpoint plus the survivors' writes in the database. On restart, `__enter__` loads the `CheckpointTuple` including `pending_writes` into `checkpoint_pending_writes`; `tick()` calls `_reapply_writes_to_succeeded_nodes`, which "Restore[s] the output of finished tasks from checkpoint to in-memory tasks" — tasks whose ids have writes get them handed back and are **not re-executed**, while "Unfinished (failed or interrupted) tasks keep empty writes, so the runner re-executes them" (`_loop.py::_reapply_writes_to_succeeded_nodes`). Task ids are deterministic (derived from checkpoint id + path in `prepare_next_tasks`), which is what makes the reapply match. The docs summarize: "if one or more nodes fail at a given superstep, you can restart your graph from the last successful step … successful nodes' writes … don't need to be re-run on resume" (checkpointers.md "Pending writes"). `_resume_error_handlers_if_applicable` additionally re-schedules error handlers for tasks that failed in the prior run (found via persisted `__error_source_node__` + `__error__` writes).

### 5.3 Time travel: replay and fork

- **Replay:** invoke with `checkpoint_id` in config. `__enter__` fetches that exact checkpoint (`self.checkpoint_config[CONF].get(CONFIG_KEY_CHECKPOINT_ID)` branch → `checkpointer.get_tuple`), `is_replaying` is set, and on the first tick tasks that already completed are re-executed only to surface cached outputs; `is_replaying = False` is cleared after the first tick (`after_tick`: "only replay (re-execute) done tasks on the first tick"). Per docs: "Nodes before the checkpoint are skipped (their results are already saved). Nodes after the checkpoint re-execute, including any LLM calls, API requests, or interrupts — which are always re-triggered during replay" (use-time-travel.md). During time-travel the loaded `__resume__` writes are dropped so `interrupt()` calls re-fire (unless actively resuming: `_first`'s `is_time_traveling` logic).
- **Fork:** if the addressed checkpoint is one the thread has already moved past (detected by `checkpoint_superseded`: compare the addressed id to the latest head — "A checkpoint with a child is never the latest put", pregel/_checkpoint.py), or it's not an update/fork checkpoint, the run saves a `{"source": "fork"}` checkpoint first so the replay creates a **new branch** rather than overwriting shared history (`_loop.py::_first`). The user-facing fork API is `graph.update_state(config_with_checkpoint_id, values, as_node=...)`, which creates a `{"source": "update"}` checkpoint "treated the same as a node update" (values pass through reducers) — "It creates a new checkpoint that branches from the specified point. The original execution history remains intact" (use-time-travel.md). `metadata.source == "update"` is how history filters find forks (checkpointers.md "Find a specific checkpoint").
- **Subgraph time travel:** without its own checkpointer, a subgraph is one parent superstep (only parent-level time travel); with `checkpointer=True`, the subgraph keeps its own per-step history under its namespace in the same thread, addressable via `get_state(config, subgraphs=True)` and forkable from inside (use-time-travel.md "Subgraphs" tabs). During parent replay, `ReplayState` (config key `__pregel_replay_state`) resolves each subgraph's matching checkpoint via the parent's `checkpoint_map`.

## 6. Backends

### 6.1 InMemorySaver (`langgraph.checkpoint.memory`)

Pure-RAM store: `storage` is a `defaultdict` keyed `thread_id → checkpoint_ns → checkpoint_id → (checkpoint_bytes, metadata_bytes, parent_id)`, plus a `blobs` dict for channel values (keyed by version) and a `writes` dict keyed `(thread_id, ns, checkpoint_id) → (task_id, idx) → (task_id, channel, value_bytes, task_path)` (memory/__init__.py). Sync and async methods are trivially the same (async delegates to sync). `get_next_version` uses the sortable `f"{next_v:032}.{random:016}"` string. `MemorySaver` is kept as a backwards-compatibility alias. Explicitly "Only use InMemorySaver for debugging or testing purposes … For production … PostgresSaver / AsyncPostgresSaver. If you are using LangSmith Deployment, no checkpointer needs to be specified" (class docstring). All checkpoints vanish on process restart (docs persistence.md troubleshooting).

### 6.2 SqliteSaver / AsyncSqliteSaver (`langgraph-checkpoint-sqlite`)

Two tables created by `setup()` (auto-invoked from its `cursor()` context manager): `checkpoints` and `writes`, with WAL journal mode; primary keys `(thread_id, checkpoint_ns, checkpoint_id)` and `(... , task_id, idx)` (checkpoint-sqlite/__init__.py::`setup`). Single connection guarded by a `threading.Lock` ("meant for lightweight, synchronous use cases … does not scale to multiple threads"). `put` uses `INSERT OR REPLACE`; `put_writes` uses `INSERT OR REPLACE` for special (negative-idx) channels but `INSERT OR IGNORE` for regular writes — making retried task writes idempotent. Channel values are stored inline in the checkpoint blob; metadata as JSON text. The sync `SqliteSaver` raises `NotImplementedError` on all `a*` methods with a pointer to `AsyncSqliteSaver` (requires `aiosqlite`). Note the schema has no `checkpoint_blobs` table — SQLite's delta-channel fast path instead uses a recursive CTE over `checkpoints` (stage 1) shipping full blobs to Python, plus a per-channel UNION ALL over `writes` (stage 2).

### 6.3 PostgresSaver / AsyncPostgresSaver (`langgraph-checkpoint-postgres`)

The production saver (used by LangSmith's own stack — docs: checkpointers.md "Checkpointer libraries"). Built on psycopg 3 with optional pipeline mode (`PostgresSaver(conn, pipe=...)`; `ConnectionPool` support; a single `Connection` may use `conn.pipeline()`). Four tables via the versioned `MIGRATIONS` list (checkpoint-postgres/base.py): `checkpoints` (checkpoint + metadata as JSONB), `checkpoint_blobs` (BYTEA per (channel, version) — dedup via `DO NOTHING`), `checkpoint_writes` (with `task_path` column added by the latest migration), `checkpoint_migrations`. `setup()` "MUST be called directly by the user the first time checkpointer is used" — it applies pending migrations in order. Read path is a single `SELECT_SQL` that lateral-joins blobs by version and aggregates writes ordered by `(task_id, idx)`. Upsert semantics mirror SQLite: checkpoints upsert (DO UPDATE — same id can be re-saved), special writes upsert, regular writes DO NOTHING. Old `v < 4` checkpoints get pending sends migrated on read (`_migrate_pending_sends`). `AsyncPostgresSaver` lives in `postgres/aio.py`; `ShallowPostgresSaver` (shallow.py) is a variant that skips subgraph write persistence. `get_next_version` is the same sortable random-hex string as InMemory.

### 6.4 TTLs and the Agent Server / platform story

**OSS savers have no built-in TTL.** None of InMemory/Sqlite/Postgres savers accept a TTL argument in current main (verified by reading their `__init__`s), and the docs' fix for "Checkpoints growing unboundedly" is to "Prune old checkpoints periodically or set a retention policy … Consider adding a cron job to delete checkpoints older than N days" (persistence.md troubleshooting). LangGraph team members confirm the split: "In LangGraph platform, we support TTLs. You can do something similar if you are just using OSS … implementing TTLs isn't that hard" (GitHub langgraphjs issue #1138 — secondary source).

On the **platform (Agent Server / LangSmith)**, TTL is a first-class config in `langgraph.json` under `checkpointer.ttl`: `{"strategy": "delete" | "keep_latest", "default_ttl": <minutes>, "sweep_interval_minutes": <n>}`, plus per-thread TTL via the Threads API (`threads.create(ttl={...})`); expired checkpoints are swept automatically (docs: configure-ttl.md; the `keep_latest` strategy maps to the OSS `prune(strategy="keep_latest")` hook — `ThreadTTLConfig` in `libs/cli/langgraph_cli/schemas.py`). The platform also **handles checkpointing automatically** — "When using the Agent Server, you do not need to implement or configure checkpointers or stores manually" (persistence.md, checkpointers.md) — and "auto-detects which capabilities your checkpointer implements at startup and activates the corresponding features": `adelete_for_runs` → rollback multitask strategy, `acopy_thread` → efficient thread forking, `aprune` → history pruning, `aget_delta_channel_history` → efficient delta channel reconstruction (checkpointers.md "Extended capabilities"). Custom checkpointers are not supported on the managed platform (support.langchain.com article — secondary). Other ecosystem savers exist (MongoDB, Azure Cosmos DB; docs list) and third parties (e.g. Redis) add their own TTL knobs — outside this repo.

### 6.5 Comparison table

| | InMemorySaver | SqliteSaver (+Async) | PostgresSaver (+Async) | Platform/Agent Server |
|---|---|---|---|---|
| Storage | RAM dicts | SQLite file, 2 tables, WAL | Postgres, 4 tables + migrations | managed (Postgres-backed) |
| Async | delegates to sync | separate `AsyncSqliteSaver` (aiosqlite) | first-class `AsyncPostgresSaver`, pipelines | server-side |
| Blobs (value dedup) | yes (version-keyed) | no (inline) | yes (`DO NOTHING` dedup) | managed |
| `setup()` | n/a | lazy via `cursor()` | **manual, required once** | automatic |
| TTL / pruning | none | none | none (manual cron) | `checkpointer.ttl`, per-thread TTL, auto-sweep |
| Production use | "debugging or testing" | demos / local | recommended | recommended (no config needed) |

## 7. Gotchas

1. **`thread_id` is mandatory with a checkpointer.** "When invoking a graph with a checkpointer, you **must** specify a `thread_id` … Without it, the checkpointer cannot save state, resume from interrupts, or enable time-travel debugging" (base/__init__.py class docstring; checkpointers.md).
2. **Checkpoints grow unboundedly.** One full-state row per superstep, every superstep, forever — no automatic pruning or TTL in any OSS saver. Mitigations: cron deletes, `prune()` (platform), `delete_thread`, or beta `DeltaChannel` for append-heavy channels like `messages` (persistence.md; checkpointers.md "Optimize checkpoint storage").
3. **Postgres `thread_id` length limit.** The column is sized; keep ids under 255 characters (persistence.md troubleshooting).
4. **State values must be serde-serializable.** Unknown Python types raise `TypeError` from the msgpack encoder unless you opt into `pickle_fallback=True` (e.g. for pandas DataFrames — checkpointers.md "Serialization with pickle"), which is itself a security trade-off since pickle loads execute code. Even without pickle, msgpack ext hooks **import and construct arbitrary modules** recorded in checkpoint data — hence the docstring's attacker-writes-to-DB warning, `LANGGRAPH_STRICT_MSGPACK=true`, and `allowed_msgpack_modules` (jsonplus.py; _msgpack.py). In permissive default mode you'll see one-time warnings per unregistered type, and the code says these "will be blocked in a future version" — plan allowlists before upgrading.
5. **`InMemorySaver` does not survive restarts**, and `SqliteSaver` "does not scale to multiple threads" (single lock-guarded connection) — both per their docstrings. SqliteSaver also raises on async methods; you must use `AsyncSqliteSaver` for async graphs.
6. **`PostgresSaver.setup()` must be called manually the first time** (migrations), unlike SQLite where it's lazy. Also requires `autocommit=True` + dict row factory (reference docs example shows the failure mode otherwise).
7. **`checkpoint_ns` and subgraphs.** Subgraph state lives in the *same thread* under namespaced checkpoint ids (`"node:task_id"`, `|`-joined). Without `checkpointer=True`, a subgraph is a single parent superstep — you cannot time-travel inside it; with it, each step inside the subgraph is checkpointed, and the parent's `checkpoint_map`/`ReplayState` resolve the matching subgraph checkpoint during replay (use-time-travel.md; `_loop.py.__enter__`). Parent→subgraph state visibility is one-way: "When a subgraph updates state, the parent graph may not see the changes immediately … each subgraph manages its own checkpoint namespace" (persistence.md troubleshooting).
8. **`update_state` never rolls back** — it forks: "It creates a new checkpoint that branches from the specified point. The original execution history remains intact" (use-time-travel.md). `as_node` may need to be explicit for parallel branches (`InvalidUpdateError`) or fresh threads.
9. **Replay re-executes real work.** "Replay re-executes nodes — it doesn't just read from cache. LLM calls, API requests, and interrupts fire again and may return different results" (use-time-travel.md warning).
10. **Interrupt resume requires the same thread and, with multiple interrupts, explicit interrupt ids** (`Command(resume={id: value})`) — enforced with a `RuntimeError` otherwise (`_loop.py::_first`).
11. **`durability="exit"` trades recoverability for speed.** "Intermediate state is not saved, so you cannot recover from system failures (like process crashes) mid-execution" (checkpointers.md). Default `"async"` still has "a small risk that LangGraph does not write checkpoints if the process crashes during execution". Also `durability` has no effect without a checkpointer (main.py warns).
12. **The base class is not abstract.** Missing methods raise `NotImplementedError` only when the engine calls them; and per the custom-checkpointer docs, a broken exact-`checkpoint_id` lookup in `get_tuple` **silently corrupts DeltaChannel state** ("the walk stops immediately and every delta channel reconstructs as empty — silently, with no error"). There is a conformance suite (`langgraph-checkpoint-conformance`) to catch this.
13. **Docstring/version drift to be aware of:** base's `Checkpoint.v` docstring says "Currently 1" while the runtime writes `v=4`; the deprecated bottom-of-file `empty_checkpoint` in base says `LATEST_VERSION = 2`. Old articles describing `ordered_map`/`ordered_lists`, `next_id`, `setup` on the base interface, or "JsonPlusSerializer is JSON" are describing pre-1.0 code. (Direct evidence: current sources above.)
14. **Cross-language checkpoints are not portable** (researcher inference from §4b: Python msgpack ext-records vs JS JSON records, plus different JS schema versions) — don't point a JS and a Python deployment at the same checkpoint database expecting interop.
